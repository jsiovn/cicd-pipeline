One small Node.js "orders" API taken through PR checks, tests, Docker images and deploys with GitHub Actions. The app is deliberately tiny: the pipeline around it is the product.

Site: [jsiovn.github.io/cicd-pipeline](https://jsiovn.github.io/cicd-pipeline/), built from [docs/measurements.md](docs/measurements.md) by [`pages.yml`](.github/workflows/pages.yml) on every push to `main`.

## The app

| Path | What it does |
| --- | --- |
| `src/server.ts` | Starts the Express 5 server on `PORT` (default 3000), logs with pino, drains connections on `SIGTERM` |
| `src/app.ts` | `GET /healthz` returns `{"status":"ok","uptime":<seconds>}` (plus `"db":"ok"`, or a 503, when a database is configured); `POST /orders` prices a cart; `GET /checkout` serves the page the E2E test drives |
| `src/db.ts` | `createDbCheck(DATABASE_URL)`: a `pg` pool and `select 1` for `/healthz`; no `DATABASE_URL` (tests, CI, the production image), no database |
| `src/checkout-page.ts` | That page: one "Đặt hàng" button that POSTs `/orders`, then shows "Đặt hàng thành công" |
| `e2e/`, `playwright.config.ts` | The Playwright smoke test; its `webServer` builds and starts the API on port 3000 first |
| `src/pricing/` | `cartTotal`, `isFreeShipping`, `shippingFee` and their unit tests |
| `src/cart/` | `fetchCart()`: loads the cart from `https://api.example.com/cart` with the global `fetch`; its test intercepts the request with MSW |
| `examples/coverage-trap/` | The Testing post's coverage demo, with its own Vitest config (not part of `npm test`) |
| `compose.yaml`, `docker/Dockerfile.dev` | The dev stack: the API with `tsx watch` and a bind mount, plus Postgres 19 (`docker compose up -d --wait`, then `curl -s localhost:3000/healthz`) |
| `scripts/build-site.mjs` | Builds the GitHub Pages site: reads [`docs/measurements.md`](docs/measurements.md) and writes `_site/index.html` with the Docker image size table (required: the script exits 1 without it) and the coverage table; no dependencies (`node scripts/build-site.mjs`) |
| `web/` | A separate Next.js 16 app (its own `package.json` and lockfile, not an npm workspace; built by [`web.yml`](.github/workflows/web.yml), ignored by the API's ESLint, TypeScript, Vitest and Docker build context): one page, `output: "standalone"` in `web/next.config.ts` (plus `outputFileTracingRoot`, so `server.js` lands at `.next/standalone/server.js` next to the root lockfile), and `GET /api/counter`, a module-scope counter that is **deliberately wrong** on serverless. `web/Dockerfile` and `web/Dockerfile.naive` (build context `web/`) are built by job `sizes` of [`image.yml`](.github/workflows/image.yml) |

```sh
nvm use            # Node 26 (.nvmrc); Node 22 and 24 are supported too
npm ci
npm run dev        # tsx watch src/server.ts
npm run lint
npm run typecheck  # tsc --noEmit
npm test           # vitest run
npm run test:coverage  # vitest run --coverage, fails below the thresholds in vitest.config.ts
npx playwright install chromium  # once: the browser for the E2E test
npm run test:e2e   # playwright test (builds and starts the API itself)
npm run build      # tsc -p tsconfig.build.json -> dist/ (tests excluded)
npm start          # node dist/server.js
```

```sh
curl -s -X POST localhost:3000/orders -H 'content-type: application/json' \
  -d '{"items":[{"sku":"TSHIRT","unitPrice":150000,"quantity":2}]}'
# {"subtotal":300000,"shipping":30000,"total":330000}
```

The Next.js app, from `web/`:

```sh
cd web
npm ci
npm run dev        # next dev
npm run lint       # eslint (eslint-config-next)
npm run typecheck  # next typegen && tsc --noEmit
npm run build      # next build -> .next/standalone/server.js
PORT=3001 node .next/standalone/server.js
curl -s localhost:3001/api/counter  # {"count":1,"processStartedAt":"..."}; again -> "count":2
```

`web.yml` has a `paths` filter (`web/**` and the workflow file) and is **not a required check**: a pull request that does not touch `web/` never starts it, so a required `Web` check would wait forever and block the merge. The ruleset requires only `ci-ok`, which runs on every pull request.

## Run it yourself

1. Fork the repository. GitHub turns Actions off in a fork: open the fork's **Actions** tab and enable workflows. Scheduled workflows stay disabled in a fork until you enable each one.
2. `ci.yml`, `docker-lab.yml` and `web.yml` then work unchanged: on pull requests and pushes to `main` (`docker-lab.yml` and `web.yml` only when their `paths` change).
3. `image.yml` pushes to `ghcr.io/jsiovn/cicd-pipeline`, which your fork cannot write to: change `IMAGE` in [`image.yml`](.github/workflows/image.yml) and [`release.yml`](.github/workflows/release.yml) to `ghcr.io/<your account>/cicd-pipeline` (the `sizes` job works either way). `jsiovn` is also hardcoded in the environment URL of `release.yml` and in `REPO` of [`scripts/build-site.mjs`](scripts/build-site.mjs), so the site links back here until you change them.
4. `pages.yml` needs Pages turned on with the source **GitHub Actions** (Settings › Pages). `release.yml` uses the environment `production` (GitHub creates it on the first run); add yourself as its required reviewer, otherwise it promotes without asking.
5. Rulesets are not copied by a fork. To get the PR gate, create a ruleset on `main` that requires a pull request and the status check `ci-ok` (setup in [docs/measurements.md › PR gate](docs/measurements.md#pr-gate)).

Locally, the commands under [The app](#the-app) need only Node and npm; the Docker scripts in `docker/` and `docker/lab/` need a running Docker daemon.

## Limits

- **Run logs expire.** GitHub deletes workflow run logs and artifacts after 90 days (the default, and the maximum for a public repository). That is why this README links workflow pages, files and pull requests, never a single run: a run link would be dead within three months. The numbers the posts quote are copied, dated, into [docs/measurements.md](docs/measurements.md).
- **Scheduled refresh.** `ci.yml`, `image.yml` and `docker-lab.yml` also run on the first day of each month (03:17, 03:37 and 03:57 UTC), so while the schedules are enabled these three workflow pages each have a run younger than 90 days. `web.yml`, `pages.yml` and `release.yml` have no schedule: their pages keep a run only for 90 days after a push that triggers them (`web/` changes, any change on `main`) or a manual dispatch. `pages.yml` has no schedule: it redeploys whenever `main` changes, and the site does not expire. A scheduled run of `image.yml` also runs `publish`, so `:main` and the `sha-<short>` tag of the current `main` commit are pushed again, rebuilt on the current base image: a `sha-<short>` tag is not immutable here. Scheduled runs share the `cancel-in-progress` concurrency group with push runs on `main`, so a push at the same moment cancels the older of the two. A scheduled run does not change docs/measurements.md: its numbers can drift from the recorded ones.
- **No keepalive.** In a public repository GitHub disables scheduled workflows after 60 days without repository activity. GitHub's documentation (checked 2026-11-22) does not define "repository activity" and does not say that re-enabling a workflow through the API resets that timer, so no keepalive job is used here; a job that commits to `main` would also have to get around the ruleset. If the schedules stop after a quiet period, re-enable them by hand: Actions tab › the workflow › **Enable workflow**, or `gh workflow enable <file> --repo jsiovn/cicd-pipeline`.
- **No Vercel preview.** A preview deploy per pull request exists only if its workflows are present; they are not (see CI/CD 6.3 and 7.2 above).
- **Package page.** A GHCR package is private when it is first published and does not inherit the repository's visibility. Until it is made public in the package settings, the package page and `docker pull ghcr.io/jsiovn/cicd-pipeline:main` need a login with access to it.
- **Article links.** The four articles go live on javascript.io.vn when they are published; until then their links return 404.
